### 1.3. Что мы отправляем в банк

| Показатель | Значение |
| --- | --- |
| Документов с `context` при retain | **15 из 40** |
| Документов с `metadata` | **0 из 40** |
| Теги | у всех 40 (`pi-hindsight`, `agent-summary`, `agent-manual`, …) |

**Вывод:** из богатого API 0.9.0 мы используем `retain` / `recall` / `reflect` / `stats` /
`deleteDocument`. Не используем: инвалидацию, `PATCH memories/{id}`, `reprocess`,
mental models, directives, `entity_labels`, `retain_strategies`, per-bank toggles
recall-стадий, knowledge pages.

### 1.4. Reflect сломан

Замеры времени ответа `POST /reflect`:

| Банк | Фактов | Время |
| --- | --- | --- |
| `argocd` | 10 | 28 с |
| `mono` | 24 | 59 с |
| `pi-hindsight` | 382 | **таймаут 300 с, ответа нет** |

Диагностика по `GET /llm-requests` (журнал LLM-вызовов самого Hindsight):

```text
op=reflect  model=gpt-5.6-luna  dur_ms=3181  status=success
llm_info: {"tool_calls": ["search_observations"], "finish_reason": "tool_calls"}
output: None
```

**LLM отработал за 3.2 секунды успешно.** Записан ровно **один** LLM-вызов; второго
(где модель получила бы результаты инструмента и сформулировала ответ) не было.
Агент reflect завис **внутри инструмента `search_observations`**, между вызовами.

Что исключено:

- не сеть и не модель — 3.2 с, `success`;
- не recall как таковой — обычный `memories/recall` на том же банке отвечает за 4–7 с;
- не объём сам по себе, но масштабирование резко нелинейное (10 → 28 с, 24 → 59 с, 382 → ∞).

Подозреваемые: 143 observation в 6 scope, из которых один — `["agent-summary","pi-hindsight"]`
на **110 записей**; и/или graph expansion по 3202 temporal-связям.

**Важное следствие:** наш клиент рвёт reflect по таймауту 30 с (`src/hindsight.ts`),
значит `op: "reflect"` в pi-hindsight **никогда не работал** — все попытки молча
падали в recall.

### 1.5. Аварийный фолбэк генерирует мусор

Наблюдённый в проде запрос к банку:

```text
рефлект может отвечать долго должны | подмешивать асинхронно наверное ответ стопариться |
точно 300 сек видимо какая-то | другая возникла проблема посмотри пожалуйста | логи hindsight
```

Это не работа модели, а `heuristicQueries()` из `src/recall-utils.ts`: при падении
query-builder'а мы выкидываем стоп-слова и **нарезаем сообщение на группы по ~5 слов
подряд**. Отсюда рубленые куски в порядке исходного текста. Такой запрос вернул
186 фактов мусора, из которых судья пропустил 8 почти случайных.

## 2. Что говорит вендор (Hindsight 0.9.0)

### 2.1. Бенчмарк убил нашу архитектуру чтения

Из блога 0.9.0 (проверено в первоисточнике,
`hindsight-docs/blog/2026-08-06-hindsight-0-9-0.md`):

> Our integrations did what most of the ecosystem does: **automatic recall on every prompt** —
> embed the message, retrieve similar memories, inject them. On the suite as it stood then,
> that scored **1.06 corrections per task versus 0.97 for no memory at all**.
> Our memory made the agent _worse_.

Два принципа, которые они из этого вывели:

> **Scattered memories break focus.** …feeding it scattered, confidently-injected fragments
> doesn't inform the mission, it _derails_ it.
>
> **Never add work to the hot path.** Per-prompt recall put a retrieval round-trip in front of
> _every single message_ — latency and noise, paid on every turn.

Это ровно то, что делает pi-hindsight: recall на каждом `before_agent_start` + инъекция
фрагментов. **Оговорка:** их вариант не имел двух наших защит — per-query судьи
(мы отбрасываем нерелевантное) и гейта по субъекту (мы умеем не ходить в банк вовсе).
Их «1.06 vs 0.97» получено на архитектуре без них. Сам бенчмарк ещё не опубликован
(обещан на agentmemorybenchmark.ai).

### 2.2. Правила курации

Из доки (`developer/memories`):

> | **Superseded by a newer fact you're storing anyway** | Just retain the new fact |
> | **No longer true, with nothing to replace it** | **Invalidate** the memory |
> | **A duplicate or superseded fact** | **Invalidate** the memory |
>
> The rule of thumb: **if Hindsight could have known, let consolidation handle it;
> if only you know, curate it.**

И предупреждение:

> reprocessing a document **resets curation** of the facts it produced.

### 2.3. `hindsight-coding-agents` (по отчёту исследования на opus-5)

- Это **не SDK**: turnkey CLI-инсталлер + готовые бандлы хуков + stdio MCP-сервер.
  В тарболе 30 esbuild-бандлов, `index.d.ts` на 3 строки.
- **Не расширяемо**: список харнессов — захардкоженный массив в `src/harness/registry.ts`,
  миссии и промпты — константы. Добавить агента = PR в апстрим.
- **pi не поддерживается**; в доке pi числится отдельно как _community_-интеграция
  (`epimetheus` от noctuid).
- «Superseded» относится **только к шести плагинам авторства Vectorize**, community-список
  не тронут.
- Ловушка: их `configureBank()` при каждом старте сессии постит манифест конфига банка
  и **перезапишет** миссии, которые ставит pi-hindsight, если банк общий.
- Их же post-mortem: **ни один их плагин не читал git** — самая дешёвая ценная идея.

## 3. Принятые решения

| № | Вопрос | Решение | Обоснование |
| --- | --- | --- | --- |
| 1 | Корень проблемы | **Факт не умеет умирать** | Дедуп при записи ловит только совпадения в момент вставки; против «было верно в июле, стало ложью в августе» он бессилен. Ужесточение экстракции уменьшило бы приток, но не тронуло накопленные 20%. |
| 2 | Кто решает, что факт мёртв | **Автоматика, не человек** | Ручная курация 1685 фактов не масштабируется. |
| 3 | Инвалидация vs консолидация | **Разделить по природе** | Консолидация — для пар «было/стало», где новый факт есть. Явная инвалидация — для сирот: дубли и удалённый код, где факта-замены не будет никогда (`review-server.ts` удалён — нового факта про него не появится). |
| 4 | Предохранитель авто-инвалидации | **Требовать улику в тексте** | Модель обязана вернуть цитату из транскрипта, подтверждающую смерть объекта. Нет цитаты — нет инвалидации. Цитата пишется в `invalidation_reason`. |
| 5 | Стратегия vs `hindsight-coding-agents` | **Отложено** | Ждали отчёт; получен (§2.3). Требует финального решения — см. §5. |
| 6 | Накопленный мусор | **Ожидает ответа** | Варианты: разовый скрипт / команда `/mem-clean` / ничего / чистка + reprocess. |
| 7 | Гибрид чтения | **Принят** | reflect на смене задачи + быстрый recall на обычных ходах. |
| 7a | Детектор смены задачи | **Ожидает подтверждения** (предложен вариант B) | Бесплатно, по расхождению субъектов между ходами. |
| 7b | Reflect | **Чинить** | Не выбрасывать: сначала диагностика (per-bank toggles, бюджет), затем асинхронное подмешивание. |
| 7c | Heuristic-фолбэк | **НЕ выпиливать** | Решение пользователя: выпиливать — «бред». Значит чинить: запрос должен состоять из осмысленных субъектов, а не нарезки по 5 слов. |

## 4. План работ

### 4.1. Чиним reflect (приоритет 1)

1. Диагностика: почему `search_observations` не возвращает управление на 382 фактах.
   Проверить per-bank toggles 0.9 (`temporal` / `graph` / `rerank`), бюджет запроса,
   `recall_max_tokens`.
2. Поднять таймаут клиента (сейчас 30 с) — reflect по природе секунды-минуты.
3. Никогда не ждать reflect на hot path: запуск в фон, подмешивание результата
   в **следующий** ход.

### 4.2. Гибридное чтение

- Обычный ход: как сейчас — 1–5 запросов, per-query судья, гейт по субъекту.
- **Смена задачи**: глубокий заход — reflect в фоне + расширенный recall,
  результат подмешивается синтезированной сводкой, а не россыпью фактов.
- Детектор смены задачи — бесплатный, по расхождению множества субъектов
  (query-builder их и так извлекает на каждом ходу) + дешёвые триггеры:
  первый ход сессии, ход после компакта.

### 4.3. Жизненный цикл факта

- Расширить вердикт DEDUP-шага с `new` / `duplicate` до `new` / `duplicate` / `contradicts:<id>`.
- `extractHits()` должен сохранять `id` факта (сейчас выбрасывает — а для инвалидации он нужен).
- Добавить в `HindsightClient` метод инвалидации (`PATCH memories/{id}`).
- Инвалидация только с цитатой-уликой; цитата → `invalidation_reason`.

### 4.4. Починить фолбэк

`heuristicQueries()` должна давать запрос из осмысленных субъектов (идентификаторы,
пути, имена файлов), а не нарезку по 5 слов. Плюс включить `debug`, чтобы видеть
`recall.gate.error` и понимать, почему падает query-builder.

### 4.5. Гигиена записи

- Заполнять `context` **на каждом** retain и по делу: дока говорит, что context решает,
  станет ли «я сделал X» фактом `experience` (агент) или `world` (пользователь).
  Сейчас 15/40 и текст описывает жанр, а не спикера.
- Заполнять `metadata` (сейчас 0/40).
- Разобраться со смешением языков (96 ru / 286 en в одном банке).
